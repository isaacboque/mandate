# Review, 2026-11-17: code, UX, UI and LinkedIn-readiness

A review of the whole repo as a skeptical senior engineer would do it before it is shown publicly, followed by the low-risk fixes. Line numbers are at commit `6e15936` (the base of this branch), so they still point at the code the finding is about. Status: **fixed** (in this PR), **ticketed** (a wayfinder ticket holds the decision or the work), **declined** (looked at, left on purpose).

## Read this first

- **One real gap in the guardrails' own story, not in their logic.** `checkCart` never checks that a price is a whole number of cents above zero, so a line priced at 0, below zero or NaN passes the budget and cap checks (F3). Nothing like that can reach it today: the fixture catalog is static, and the Channel3 mapping now drops such offers (fixed in this PR, test-first). Making `checkCart` itself fail closed changes what a guardrail blocks, so it is **ticket 08, a decision for Isaac**, not code in this PR. Until then the claim "the guardrails fail closed" is true for missing and malformed data (dates, sizes, categories) and not for a nonsense price; the docs now say so.
- **No guardrail was loosened or changed.** `src/mandate/check.ts`, the oracle and the scenarios are untouched. The eval is still 46/46 (27/7/12) and the mutation run still catches 10 of 10, with the same per-guardrail numbers as `docs/MUTATION.md`.
- **The most valuable change for the LinkedIn visitor** is F1 and F2: a first visit to the free-tier demo used to show a blank page for up to 30 s, and the attack demo made you read a generic red banner to understand what happened.
- Not measured in this review: a real LLM (opt-in `eval:real`, ticket 04), the hosted Render URLs (this run could not reach them, ticket 06), real PayPal.

## Findings, most severe first

### High

**F1. UX: a sleeping free-tier server looked broken.** `web/src/App.tsx:38` loaded config and proposals with no loading state; until the server woke up nothing rendered under the stepper, and a 502 showed the raw parse error ("Unexpected token <"), because `web/src/api.ts:45-46` called `r.json()` without looking at the status. *Why it matters:* the README tells people the demo "can take about 30 s to wake up"; the first impression for every LinkedIn visitor is that wait. *Fix:* after 2 s the page says "Waking up the demo… Ns" and why; a failure shows "Try again"; 502/503/504 and offline errors have plain messages (`friendlyError`); every API read checks the status. *Status: fixed.* Verified in Chrome with a 3.5 s delayed `/api/config` and a forced 502 (screenshots `mobile-cold-start.png`, `mobile-server-down.png`).

**F2. UX: the "poisoned listing is blocked" moment was there but had to be read.** The attack button was a small ghost button explained only by a tooltip (`App.tsx` Ask step), and the result was the generic "Blocked: 3 of 10 checks failed" banner. *Why it matters:* this is the whole pitch. *Fix:* a three-line story on the blocked card (what the listing told the model, what the fooled model proposed, which guardrails stopped it, and "no money moved"), built only from the proposal the server returned (`web/src/attack.ts`, tested); a visible sentence under the Ask box says what the button does. *Status: fixed.*

**F3. Code: a nonsense catalog price passes the money guardrails.** `Channel3Catalog.ts:89` accepted any `typeof price === "number"`, so 0 or a negative price became a product (`:108`), and `check.ts:30,39` compare with `>` only: `NaN > cap` is false and a negative price lowers the total. The architecture doc says the guardrails "fail closed when data is missing". *Why it matters:* that sentence is the kind a reviewer tests. *Fix:* the catalog mapping drops offers under one cent before choosing "cheapest" (so a free decoy cannot win or hide a valid offer); the claim is softened in README, ARCHITECTURE, CASE-STUDY and THREAT-MODEL. *Status: fixed at the catalog boundary; guardrail-level fix ticketed (08, decision).*

### Medium

**F4. Code: a double click could capture twice or show an error.** `service.ts:225` (`approve`) and `:241` (`pay`) awaited between "is it still pending?" and acting. Two quick clicks: the second `approve` threw "already approved"; the second `pay` re-ran the checkout checks and logged a second capture. PayPal would refuse a second capture, but the UI could show a paid purchase with an error. *Fix:* a second call joins the run in progress. Test: two concurrent clicks give one `payment.captured` event and no error. *Status: fixed.*

**F5. Code: a hung model hung the request.** `agent.ts:95` and `draft.ts` called `generateText` with no timeout, so a stuck provider held the visitor's request until the proxy cut it. *Fix:* a 40 s cut-off (`LLM_TIMEOUT_SECONDS` to change it); the rules agent or reader answers and the summary says "took too long". *Status: fixed.*

**F6. Code: the audit export mixed in other purchases.** `service.ts:120` matched trace events with `includes(id)`, so `prop_x_1` also matched `prop_x_10`, `prop_x_11`... The audit JSON is the "proof" artifact of a purchase. *Fix:* ids are matched whole (quoted). Test with 10 proposals. *Status: fixed.*

**F7. Code: a mandate could carry any integer.** `app.ts:14` allowed up to 2^53 cents, where sums and products stop being exact. *Fix:* every amount is at most 1,000,000.00 (decision under "Decisions" in the PR). *Status: fixed.*

**F8. Code: no body limit, no browser headers, API 404 served HTML.** `app.ts` parsed any size of body, sent no `nosniff` / frame / referrer headers, and an unknown `/api/...` GET fell through to the web page's HTML fallback. *Fix:* 32 KB limit (413 JSON), four headers on every answer, JSON 404 under `/api`. A Content-Security-Policy is ticket 11 (a wrong one blanks the demo). *Status: fixed; CSP ticketed.*

**F9. Code: the per-visitor limit trusts a header the client can set.** `app.ts:29` uses the first `X-Forwarded-For` entry. A client can rotate it. The instance-wide daily cap still bounds the quota. *Status: ticketed (07, needs a look at the hosted proxy chain).*

**F10. Code: traces are never deleted.** `trace.ts:45`, `deps.ts:26`: one JSONL file per session under `traces/`, containing what visitors typed, forever. *Status: ticketed (09).*

**F11. UI: the phone stepper had no names.** `styles.css:175` set `display: none` on the step labels at 560 px, so a screen reader announced "2", "3", "4". *Fix:* visually hidden, still announced. Verified in Chrome (4 of 4 named at 380 px). *Status: fixed.*

**F12. UI: contrast below AA.** Computed with the WCAG formula: green on its soft background 4.32:1 (`--good`, used by the "Inside your mandate" banner, "Paid" badge and status pills), trace timestamps 3.36:1. *Fix:* `--good` is now 5.43:1 on the soft background (6.19:1 on white); timestamps 5.01:1. Everything else I computed passes (muted text 4.6 to 5.4, badges 4.8 to 6.0, white on brand 7.1). *Status: fixed.*

**F13. UX: an opened trace event jumped to another event.** `App.tsx:660` keyed events by their position in a reversed list, so every new event shifted which one was "open". The trace panel also polled every 1.5 s in a hidden tab (`:646`). *Fix:* stable keys (tested), polling pauses when the tab is hidden. *Status: fixed.*

**F14. UX: focus stayed on a button that no longer exists.** Moving between the four steps replaces the panel; keyboard and screen-reader focus fell back to the page. *Fix:* the new panel takes focus. *Status: fixed.*

**F15. UX: the story hid that it is a demo.** Nothing on screen but a badge said "no real money". *Fix:* a footer line in both modes ("a fixture catalog and simulated payments..." / "the PayPal sandbox. No real money moves."). *Status: fixed.*

**F16. LinkedIn: absolute claims.** "cannot move money", "the eval proves it", "fail closed whenever data is missing", "Everyone is building..." appear in the README, case study and posts. The evidence is a scripted eval with an independent oracle and 10/10 mutants, plus the structural fact that the agent has no paying tool: strong, but not "cannot" or "proves". *Fix:* each is reworded to what was measured ("in the 46-scenario eval it never did"). *Status: fixed.*

**F17. LinkedIn: numbers drift.** `npm test` is now 197 tests (was 177). README and LINKEDIN quoted 177. *Fix:* both updated; MAP and ticket 03 are dated records and keep the numbers of their day. *Status: fixed.*

**F18. CI: not what the README implies.** `.github/workflows/ci.yml:14` runs `npm install`; `package.json:22` allows Node 18 while everything else says 20; nothing runs `npm audit` (0 vulnerabilities today); the mutation claim is checked inside `npm test` but not visible as a step. *Status: ticketed (10): touches the workflow and `package.json`, which this task did not list.*

## What I looked at and found sound

- **Money is integer cents everywhere it matters.** `core/money.ts`, `parseMoney.ts` (rejects what it cannot read, tested with locale cases), the PayPal mapping (`major()` goes through `toFixed(2)` only at the edge). No float arithmetic on amounts.
- **The guardrails' structure.** Pure function, fixed order, one result per name; expiry and freshness fail closed on unreadable dates; the cumulative budget is applied at proposal and again at checkout; the checkout re-check re-reads the live price.
- **The agent cannot pay.** Three tools, `propose_cart` rejects ids the catalog did not return in this run, and the model prompt carries only mandate facts, never product text (`quoteUntrusted` JSON-encodes and clips it).
- **Sessions.** Cookie is HttpOnly, SameSite Lax, secure behind HTTPS; ids are validated by regex; the store sweeps idle sessions and caps at 300.
- **Tests.** They assert behaviour (outcomes, traces, HTTP status) rather than mirroring the implementation; no timers, randomness or order dependence found; the mutation test makes the eval itself falsifiable. Gaps closed here: HTTP hardening, concurrency, audit ids, model timeouts, catalog price sanity.
- **Dependencies.** `npm audit --omit=dev`: 0 vulnerabilities.
